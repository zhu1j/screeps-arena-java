# 001 迁移到"惯用 Java"API 风格

状态：想法 · 未排期

## 背景

v0.1 选了 API 方案 3 —— **全包装领域模型**：每个游戏对象（`Creep`、`StructureSpawn` …）
都包一层 Java 类，对局里的对象是 Java 对象，不是活的 JS 对象。

这个选择是刻意的：现阶段主要目的是**顺便学 Java**。包装层能强制用上类型、封装、
集合、继承这些语言设施，读起来也更像一本 Java 教材，而不是"Java 语法的 JS"。

## 想法

以后可以迁到方案 1 —— **惯用 Java**：去掉包装层，让 Java 侧的游戏对象**就是**那个活的
JS 对象，上面只叠 `List`、枚举和工具类。

具体的实现路径有两条：

1. **彻底换底**：删掉包装类，直接把 `@JSObject` 接口暴露成公开 API，
   加一层静态工具类提供集合化便利（`Creeps.my()` 返回 `List<Creep>`）。
2. **保留外观**：公开 API 的签名完全不动，只把包装类内部从"持有 raw 引用 + 转发"
   改成"本身就是 raw"。调用方代码零改动。

方案 2 更平滑：v0.1 的 bot 代码不用重写，纯粹是内部实现的替换。

## 收益

- 少一层对象，少一次属性转发。属性读写直接落在 JS 对象上
- 和官方 TypeScript 写法一一对应，查文档、抄思路时不用做心智翻译
- 对象身份天然稳定，不需要 v0.1 里那套按 id 缓存包装对象的结构

## 代价

- 失去"在 Java 类里加自己的字段和方法"的能力。跨 tick 状态只能回到静态字段，
  或者给 JS 对象挂属性（`creep.initialPos = ...`）
- 公开 API 会直接暴露 TeaVM 的 `JSObject`，绑定库和编译器绑得更死，以后换编译路线更难

## 什么时候值得做

当出现下面任一情况时再考虑：

- 发现包装层成为性能瓶颈（比如每 tick 要遍历几百个对象）
- 需要频繁和官方 TypeScript 代码做对照移植
- 想把 API 做成"薄到几乎没有"的风格
